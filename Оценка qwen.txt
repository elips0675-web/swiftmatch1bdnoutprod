Оценка проекта SwiftMatch1BD
Комплексный аудит по состоянию на 22.08.2026, на основе AGENTS.md, README, «Что доделать.txt», «Для анализа.txt».
📊 Общий вердикт
Уровень зрелости: 8/10 для pet/startup-проекта, 6.5/10 для production-ready SaaS.
Проект прошёл 33 итерации разработки с дисциплинированным подходом: каждый аудит предыдущих моделей (kimi / qwen / deepseek) закрывался конкретными этапами с фиксацией граблей в AGENTS.md. Это редкий случай, когда техдолг не копится, а системно разбирается.
Главное достижение: 231/231 тестов зелёных + E2E + сборка + Android APK. Это не «работает на моей машине» — это инженерная база.
Главный риск: проект застрял в «последней миле» — код готов, но нет ни staging, ни реальных ключей, ни выпущенного Android-релиза. Доход от него пока 0 ₽.

SameSite=Lax + строгий CORS — достаточно для current setup. Но если API когда-нибудь вынесут на поддомен — потребуется double-submit token. Задокументировано в ADR.

💡 Неожиданные находки
AGENTS.md — это актив, а не документация. 30+ зафиксированных граблей с точными симптомами — это то, что отличает «живой» проект от «мёртвого». Продолжайте в том же духе: каждый production-инцидент → новая запись в AGENTS.md.
Миграция на httpOnly cookie (этап 33) — образцовая. Сохранена обратная совместимость с E2E через чтение legacy-storage, /me probe всегда 200 (иначе audit падает), нативные сборки работают через Bearer. Это решение в ADR — правильное.
EXPLAIN-аудит (этап 31) — недооценённая практика. Нашли 2 скрытых 500, которые не ловились тестами (iap.js webhook, location.js). Стоит добавить в CI: статический аудит SQL против схемы перед каждым PR.
k6-лимит — это не баг, а фича. 600/мин глобальный + 30/мин лайки — с одного IP полный ramp невозможен. Это осознанно, но означает, что реальная нагрузочная ёмкость неизвестна. Нужен staging с multi-IP.
Windows-центричность — стратегический риск. Весь workflow построен на Laragon + PowerShell + Task Scheduler. Это работает для соло-разработки, но делает проект непереносимым. Docker Compose — правильный путь, но он не стал основным.
🎓 Итоговая рекомендация
Проект готов к «первому пользователю», но не к «первому миллиону».
Следующий шаг — не писать новый код, а разблокировать продакшен:
VPS + ключи → первый реальный платеж через Stripe.
Домен + keystore → первый реальный Android-пользователь.
Staging + k6 100 VU → понимание реальной ёмкости.
Всё остальное (CSRF, Storybook, SMS-верификация, AI-модерация) — это оптимизация, а не блокеры. Текущее состояние — это лучшие 70% готовности, которые я видел у pet-проектов такого масштаба.
Если нужно — могу детально разобрать любую из областей (например, составить чек-лист релиза Android или план миграции на staging).
