Оценка проекта SwiftMatch
Общее впечатление: очень зрелый production-ready проект уровня strong middle+/senior team. Видна серьёзная инженерная культура — редкость для dating-app стартапов. Разберу по пунктам.
✅ Сильные стороны (9-10/10)
1. Архитектура и стек
Правильный выбор стека: Express + MySQL + Redis + Socket.IO + Bull Queue — классическая надёжная связка для real-time приложения.
Spatial search через ST_Distance_Sphere + SPATIAL INDEX — единственно верный подход для гео-дейтинга (в отличие от постгрес-PostGIS конкурентов, тут MySQL-специфика учтена).
Разделение на очереди (email/push/image) через Bull — image-resize не будет блокировать auth.
Redis lazy-init + graceful fallback без Redis — отлично для dev/prod parity.
2. Безопасность
helmet, rate-limit (разные лимиты на auth/обычные), idempotency для Stripe — все critical paths закрыты.
Sentry с beforeSend-фильтрацией PII — правильно, иначе email/токены улетают в логи Sentry.
JWT + refresh tokens + user_sessions таблица — можно отзывать сессии.
Авто-эскалация репортов (1→pending, 3→temp ban, 5→perm ban) — хорошая защита от троллей.
3. Observability и DevOps
Prometheus + Grafana с 7-панельным дашбордом + k6 load test — это уровень enterprise.
Health checks (/health/live, /health/ready), graceful shutdown с таймаутом — k8s-friendly.
GitHub Actions: lint → test → E2E → deploy — правильный pipeline.
X-Request-Id + Winston в JSON — трассируемость запросов.
API versioning (/api/v1 + X-API-Version) — продумано на будущее.
4. Тестирование
226 тестов (126 server + 56 frontend + 44 E2E Playwright) — 0 failures. Это редкость.
Pre-flight check:ports — защита от конфигурационных косяков.
E2E покрывает critical paths: audit, features, login, profile, register.
5. Product features
GDPR compliance (consent_log, data_erase_requests) — обязательно для EU.
Safety: date check-in + emergency contacts — киллер-фича для женской аудитории.
Attachment style compatibility — психологически обоснованный matching.
A/B testing + feature flags + experiments — data-driven подход.
AI icebreakers с fallback из БД — деградация без OpenAI ключа.
6. Документация
README — образцовый: quick start, структура, чек-лист прода, таблица ключей, статусы фич. Так должны выглядеть все проекты.
🔴 Критические проблемы (требуют фикса до прода)
1. Баг в matches — возможны дубликаты
sql

1
Нет CHECK (user1_id < user2_id). Приложение может вставить (1,2) при первом лайке и (2,1) при ответном — получится два мэтча между одной парой.
Фикс: либо CHECK-констрейнт + сортировка на бэке, либо UNIQUE (LEAST(user1_id,user2_id), GREATEST(...)) через generated columns.
2. Архитектурный баг в posts
sql

12
Это user-specific флаги, но лежат в общей таблице posts. Если Вася лайкнул пост — is_liked=1 для всех? Это сломает UI.
Фикс: убрать из posts, читать через LEFT JOIN post_likes WHERE user_id = ?.
3. Sentry error handler в неправильном порядке
js

12
Sentry's error handler никогда не сработает — Express не дойдёт до него. Ошиби уходят в /500, но не в Sentry.
Фикс: initSentry(app) сразу после app.use(metricsMiddleware), до всех роутов.
4. dev-login без защиты по NODE_ENV
js

12
В проде любой может залогиниться как user#2. Нужен if (process.env.NODE_ENV !== 'development') return next().
5. CORS fallback на '*'
js

1
Если CORS_ORIGIN не задан в проде — CORS открыт для всех доменов. Для API-only JWT это менее критично, но всё равно risk. Лучше падать с ошибкой, если в проде нет CORS_ORIGIN.
🟠 Средние проблемы
6. Дубликаты ALTER в схеме
sql

12345678
Выглядит как следы итеративной разработки. Для чистого деплоя с нуля — мусор. Для миграций — ок, но надо комментировать.
7. password_hash в SELECT при логине
js

1
Поднимается в rows[0], потом не используется. Лучше не поднимать лишнего в память. Мелочь, но паттерн плохой.
8. subscriptions без защиты от дублей
Нет UNIQUE на (user_id, is_active). При race condition на webhook Stripe можно получить две активные подписки. Нужна проверка SELECT ... WHERE user_id=? AND is_active=1 AND expires_at>NOW() перед созданием + транзакция.
9. content_config JSON без валидации схемы
Админ может записать мусор в interests/banned_words — фронт упадёт. Нужна Zod-валидация на write.
10. user_profiles.id без AUTO_INCREMENT
sql

12
Это 1-to-1, но при создании profile нужно вручную передавать id. Не ошибка, но создаёт риск рассинхрона при баге в auth-flow. Альтернатива — users и user_profiles объединить, либо добавить ON INSERT триггер.
🟡 Мелочи
user_sessions.token VARCHAR(500) — избыточно, JWT обычно ≤ 256. Но не критично.
fcm_tokens UNIQUE по token(255) — префиксный индекс, норм.
analytics_events на BIGINT — правильно, при 1M events/day INT упрётся за 2 года.
compatibility_scores — симметрия не гарантирована схемой, но сиды покрывают все 9 пар. Хрупко.
Нет индекса на chats.group_id — при росте групп будет slow query.
