🔴 Пробелы и риски
1.1. Rate-limit и lockout — in-memory (блокер при горизонтальном масштабировании)
express-rate-limit и lockout.js используют in-memory хранилище. При запуске через PM2 cluster mode или Docker Compose с несколькими репликами лимиты не shared. Злоумышленник может обойти lockout, чередуя запросы между воркерами.
Фикс: Подключить rate-limit-redis и переписать lockout.js на Redis (или документировать: «prod — strictly single-instance до миграции на Redis store»).
1.2. Отсутствие __Host- prefix у cookie
sm_token без префикса. Если в будущем появятся поддомены (например, admin.swiftmatch.app), cookie может быть перезаписана/считана с поддомена.
Фикс: __Host-sm_token (требует Secure и Path=/, что уже так).
1.3. Cleanup revoked refresh-токенов
Сейчас revoked-токены помечаются revoked=1, но не удаляются (это правильно для детекта reuse). Однако через год таблица refresh_tokens разрастётся. Нет cron-джобы для удаления токенов старше N дней.
Фикс: Ежедневный cleanup: DELETE FROM refresh_tokens WHERE revoked = 1 AND updated_at < NOW() - INTERVAL 30 DAY.
1.4. WS reconnection — токен в handshake
При reconnect WebSocket клиент снова проходит handshake. Но что если refresh произошёл между disconnect и reconnect? Старый handshake.auth.token (access) уже invalid, а новый клиент не знает, потому что httpOnly cookie не читается из JS.
Проверить: Передаёт ли клиент в WS handshake только access-токен? Если да, то после silent refresh на REST клиент должен явно переподключить WS с новым токеном. Это потенциальная race.
1.5. Admin TOTP — отложено, но админка уже защищена только паролем
В «Что доделать.txt» сказано «админка не торчит наружу», но это предположение. Достаточно одной утечки admin@mail.ru/demo123456 (или XSS на фронте, или keylogger) — и злоумышленник в админке.
Рекомендация: Перед staging добавить хотя бы IP-whitelist для /api/admin/* (nginx allow/deny) или базовую HTTP Basic Auth на nginx-уровне как временную меру.
1.6. CORS для Capacitor vs строгий CORS_ORIGIN
В README написано cors({ origin: '*' }) для Capacitor, в «Для анализа.txt» — fail-fast без CORS_ORIGIN. Нужно убедиться, что нативный режим определяется по User-Agent/заголовку, а не просто отключает CORS глобально. Иначе в проде будет * для всех.
2. Риски миграции на прод
🔴 Высокие риски
2.1. Docker Compose не прогонялся end-to-end
«Локально не поднимался — нет Docker на машине». Это значит, что на staging могут всплыть проблемы: сеть между app и nginx, volumes для MySQL, healthcheck тайминги, proxy_read_timeout для WS.
Действие: Первый деплой на staging должен быть только Docker Compose + healthcheck + smoke-тесты. Не пушить код пользователей в первый же деплой.
2.2. mysqld RADAR_PRE_LEAK_64 — нехватка памяти
E2E (3 chromium + node + vite + mysql) убивал mysqld. На VPS с 1-2 GB RAM это повторится при k6 100 VU + реальные пользователи.
Действие: На staging провести k6 100 VU с мониторингом free -m и SHOW STATUS LIKE 'Threads_connected'. Возможно, DB_POOL_MAX=20 слишком много для малого VPS — уменьшить до 10.
2.3. Graceful degradation — граничные случаи
Таблица
Сервис	Без ключа	Риск
Stripe webhook	502/503	Пользователь не может оплатить, но знает об ошибке
RevenueCat webhook	503	IAP не работает — критично для монетизации
Redis	In-memory fallback	Bull Queue без Redis — падает или теряет задачи? Нужно проверить: если REDIS_URL=invalid, очереди email/push/image — они in-memory или reject?
2.4. PM2 vs Docker — конфликт стратегий
В README — pm2, в Docker Compose — docker. Если выбрать PM2 cluster mode — сломаются in-memory rate-limit и lockout. Если Docker — нужен orchestrator (docker-compose на одном хосте ок, но при росте — swarm/k8s).
Рекомендация: Для старта — Docker Compose single-instance + Redis. PM2 оставить как fallback.
2.5. Откат миграций — только через бэкап
Это ок, но rollback-plan.md должен содержать точное время RTO (Recovery Time Objective): сколько минут на restore из бэкапа? Проверено ли restore на чистой БД за последнюю неделю?
🟠 Средние риски
2.6. Nginx proxy_read_timeout 86400s
Если это глобальная директива, а не только для /socket.io/, то обычные HTTP-запросы тоже будут ждать 24 часа. При DDOS или медленных клиентах это исчерпает соединения.
Фикс: proxy_read_timeout 86400s; только в location /socket.io/.
2.7. SSL auto-renewal
Let's Encrypt требует обновления каждые 90 дней. Нет упоминания о certbot в Docker Compose или cron.
Действие: Добавить certbot контейнер или документировать ручное обновление.
