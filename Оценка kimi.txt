Провёл аудит по четырём направлениям: безопасность (фокус на cookie-схеме), риски прод-миграции, приоритизация оставшегося и слепые зоны тестов.
1. Безопасность
Cookie-схема (этап 33) — что хорошо
httpOnly sm_token/sm_refresh с корректными флагами (SameSite=Lax, Secure в проде).
XSS-safe: web-фронт не пишет токен в localStorage/sessionStorage (только память + чтение легаси для совместимости).
Гибрид Bearer/cookie покрывает и web, и нативные сборки.
Пробелы и риски
Таблица
Риск	Уровень	Почему
CSRF без double-submit token	🔴 Высокий	SameSite=Lax не защищает от same-site атак (поддомены, XSS на субдомене, open redirect). При выносе API на отдельный домен это станет критичным.
Нет rotation refresh-токенов	🔴 Высокий	Если sm_refresh украден (malware, XSS на поддомене), атакующий получает 7-дневное окно. Нет механизма инвалидации всех сессий пользователя.
Нет привязки сессии к устройству/IP	🟡 Средний	Украденный токен работает с любого устройства. Нет fingerprinting'а.
Brute-force на auth слабый	🟡 Средний	60 req/min = ~1 запрос/сек. Для логина это много. Нет account lockout после N неудач.
Race condition на refresh	🟡 Средний	Два параллельных POST /api/auth/refresh с одним sm_refresh создадут два новых access-токена. Один из них «осиротеет» и вызовет цикл 401→refresh.
WebSocket auth через query-param?	🟡 Средний	Не видел в сниппетах, но если токен передаётся в ?token= при WS handshake — он осядет в логах nginx/proxy.
Нет 2FA для админки	🔴 Высокий	admin@mail.ru / demo123456 — единственный фактор. При компрометации одного пароля — полный доступ к банам, имперсонации, рассылкам.
Быстрые фиксы (до продакшена)
Refresh rotation: при refresh выдавать новую пару access+refresh, старый refresh инвалидировать (хранить token_family в БД).
Account lockout: после 5 неудачных попыток — блокировать IP/аккаунт на 15 мин (отдельный rate-limit, строже authLimiter).
Session list / revoke all: endpoint для инвалидации всех refresh-токенов пользователя (при смене пароля, подозрении на взлом).
Admin TOTP: минимум TOTP для /api/admin/* (Google Authenticator).
2. Риски миграции на прод
🔴 Критичные
Таблица
Риск	Последствие	Митигация
Cookie-migration для существующих пользователей	Все текущие Bearer-токены в localStorage станут невалидными при переходе на cookie-only. Массовый logout.	Graceful period: 2 недели принимать и Bearer (из заголовка), и cookie. Фронт пытается сначала cookie, fallback на Bearer из памяти.
Schema drift на проде	История показывает постоянный дрейф (invites, subscriptions, location, messages). На проде SHOW COLUMNS может отличаться от локальной БД.	Добавить в CI шаг schema:validate — сравнение mysql_schema.sql с information_schema на staging перед деплоем.
Docker Compose не тестировался	«Локально не поднимался — нет Docker на машине». На проде первый запуск Docker = неизвестные ошибки конфигурации.	Поднять staging в Docker перед продом. Проверить healthcheck'и, volume permissions, сеть между app↔nginx↔Prometheus.
Redis single point of failure	Redis теперь поднят локально, но на проде (VPS) может упасть. Fallback на in-memory не тестировался под нагрузкой.	Нагрузочный тест с REDIS_URL=invalid — убедиться, что кэш промахи не DDOS'ят MySQL, а queue fallback не теряет email'ы.
Android: LAN IP + cleartext	VITE_API_URL = LAN IP, cleartext: true в capacitor.config. Если это попадёт в production APK — MITM.	Жёсткий guard в CI: если NODE_ENV=production и cleartext=true — fail build. Для релиза только домен + SSL pinning.
🟠 Средние
Stripe/RevenueCat webhooks: без ключей — 502/503 (осознанно). Но с ключами и при недоступности Stripe — нет circuit breaker'а. Можно накопить очередь необработанных webhook'ов.
Backup retention 7 дней: для GDPR и финансовых транзакций мало. Рекомендую 30-90 дней для БД, 1 год для бухгалтерских данных (платежи).
No migration rollback: в migrate.js нет down-миграций. Если миграция сломает прод — только restore из backup.
3. Приоритизация оставшегося списка
До продакшена (блокеры)
Staging + real keys + E2E — без этого нельзя проверить реальные платежи, пуши, email.
CSRF double-submit token — при текущей архитектуре (web ↔ API на одном домене — ок, но при разделении — критично).
Refresh token rotation + revoke all sessions.
Account lockout / brute-force protection на auth.
Admin 2FA (TOTP).
Schema validation CI step (mysql_schema.sql vs information_schema).
Redis failover test (убедиться, что fallback не ломает кэш-инвалидацию).
Первые 2 недели после запуска
k6 100 VU на staging — проверить RADAR_PRE_LEAK_64 под реальной нагрузкой.
Circuit breakers для Stripe, OpenAI, S3 (не пытаться бесконечно при недоступности).
SSL + auto-renewal (Let's Encrypt в docker-compose/nginx).
Android release: keystore, AAB, Google Play политика 17+ (датинг = строгая модерация).
Log aggregation (не только Winston на диск, а centralized — Loki/ELK).
Первый месяц
Design System / Storybook — не начато, но при команде >1 человека это тормозит.
Grafana alerts — не только dashboards, а alerting в Telegram/Slack (CPU, 5xx, DB connections).
SMS верификация (Twilio keys).
AI модерация фото (Rekognition/OpenAI keys).
CDN/S3 (AWS keys).

Migration idempotency	Миграции заявлены как idempotent, но нет теста повторного запуска.	CI: запустить migrate.js дважды подряд, ожидать 0 errors.
Security headers	Нет тестов на CSP, HSTS, X-Frame-Options.	Unit: supertest на /health, проверить заголовки Helmet.
Admin impersonation security	Нет тестов на то, что админ не может имперсонировать другого админа или себя.	Unit: POST /api/admin/impersonate/:id с role=admin target → ожидать 403.
